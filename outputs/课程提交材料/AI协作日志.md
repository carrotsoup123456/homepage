## 〇、AI 使用原则（我的自我约束）

1. **AI 作为协作者而非替代者**：AI 负责脚手架、样板、调试、文档整理；产品定位、内容取舍、设计决策由我主导。

3. **不盲从 AI 输出**：AI 的每次方案都经过验证；失败时由我判断并选择替代路径（见第三节案例）。

## 二、标准 2：批判性评估（多轮验证与修正）

**核心证据：6 个「AI 首方案失败 / 需修正 → 我判断并修正」的案例。**

### 案例 A：部署方式选型（GitHub Actions → gh-pages 分支）

- **AI 首方案**：用 GitHub Actions workflow 自动构建并部署到 Pages。
- **现象**：线上地址一直加载**源码版** `index.html`（`/src/main.js` 404、`%BASE_URL%favicon.svg` 未被替换），页面空白。
- **我的判断**：不是代码问题，而是「部署源」与「构建产物」不匹配——仓库配置的是「从 main 根分支部署」，但 main 是源码目录，不是构建产物。
- **修正**：改用 **gh-pages 分支静态托管**（把 `npm run build` 的 `dist` 推到 gh-pages 分支，Pages 源设为 gh-pages）。补充踩坑：`build_type` 需为 `legacy`、并加 `.nojekyll` 才生效。
- **结果**：线上正常渲染 ✅
- **评估**：AI 的默认方案（Actions）本身通用，但**未结合本仓库的部署源配置**；我没有照单全收，而是从现象反推根因并改道。

### 案例 B：联系表单后端选型（Formspree → FormSubmit）

- **AI 首方案**：用 Formspree 收留言。
- **现象**：注册后卡在**邮箱验证死循环**——点验证链接不断新开 Formspree 页面。
- **我的排查**：先排除网络问题（`formspree.io` 直连 HTTP 200），确认是 Formspree 侧的验证缺陷，遂决定**放弃**。
- **备选验证**：AI 提出 Web3Forms → 我实测发现该网络下 `web3forms.com`/`api.web3forms.com` **返回 403**（带浏览器 UA 仍 403）→ 不可用。
- **修正**：改用 **FormSubmit**（`formsubmit.co` 直连 200），无需注册、首次激活后即可收信。
- **结果**：线上端到端提交成功，留言直达邮箱 ✅
- **评估**：我**逐一实测**了 AI 给出的备选，而非假设可用；最终选择基于客观连通性证据。

### 案例 C：端到端测试「假失败」（hash 路由不重载文档）

- **现象**：线上表单测试首次返回「Form not found」。
- **AI 倾向**：可能怀疑是接口/激活问题。
- **我的诊断**：curl 同一请求却 `success:true` —— 差异在于**测试走的 hash 路由跳转（`#/`→`#/contact`）不会重新加载文档**，浏览器仍在跑**旧缓存 bundle**（含 Formspree 占位）。
- **修正**：用**带时间戳的整页重载**（`?t=xxx#/contact`）强制加载新 bundle 再测。
- **结果**：显示「✅ 已收到你的留言！」 ✅
- **评估**：这是典型的「不能只看测试结论，要看测试方法本身是否有效」。

### 案例 D：字体渲染与语义细节

- **AI 建议**：化学式可直接用 Unicode 上标 `Cu²⁺`。
- **我的判断**：Unicode 上标在不同字体下可能显示异常。
- **修正**：改用 HTML `<sup>` 渲染 `Cu<sup>2+</sup>`，保证跨平台一致。
- **评估**：对 AI 的「够用」建议提出更稳妥的工程做法。

### 案例 E：参考作品集重设计的「侵权红线」（学习模式 ≠ 复刻表达）

- **我的诉求**：提供 4 张 land-book 参考图（Bayshore / Alethia / Amperos 等），希望「照着做」一个 V3。
- **AI 的诚实提示**：参考作品的**思想、模式、布局**属于可学习范畴，但**逐一复刻其具体视觉表达（图片素材、独特图形）会构成侵权**。
- **我的判断**：认可该提示，决定**只提取设计语言**（配色关系、排版结构、构图方式），并**用 AI 生图产出原创背景素材**替换参考图中的图片。
- **结果**：V3 拥有独立原创素材，风格借鉴但表达原创 ✅
- **评估**：这是 AI 帮助我避免法律风险的正面案例——**AI 不只产出方案，也提示边界**；最终决策仍由我作出。

### 案例 F：AI 生图水印 与 整页截图的合成 bug（两个工程细节）

- **子问题 1**：DeepWorks 生图默认在右下角叠加「DeepWorks AI」水印，直接上线观感差。
  - **我的处理**：用 Python PIL 裁剪右下角区域后导出 JPEG，再放入页面。
- **子问题 2**：V3 浅色整页截图出现「画面平铺重复」的错位。
  - **AI 初判**：疑似页面 CSS 问题。
  - **我的诊断**：深色截图正常、仅浅色异常，且错误形态是**同一屏内容平铺**——这是 `captureBeyondViewport` 与 `will-change` / `sticky` 背景的 **Chrome 合成 bug**，非页面代码问题。
  - **修正**：冻结 hero 的 `vh` 高度、关闭合成相关属性，并**重建全新渲染目标**后再截图。
- **结果**：截图与线上渲染均正常 ✅
- **评估**：再次印证「测试工具本身可能骗人」——不能把工具异常当成产品缺陷。

### 案例 G：5 项动态效果的实现与「如何证明它真的在动」

- **我的诉求**：在已上线的 V3 上再加几个动态效果，但**不要引入新依赖**，并且要能在系统「减少动态效果」时自动降级。
- **AI 方案**：纯 CSS 动画 + 少量原生 JS，落地 5 项——① 首屏进场编排（`@keyframes heroEnter/cueEnter` 按 0.05→0.9s 依次进场）；② 森林萤火虫（22 个 span，CSS 随机尺寸/时长/位移 + 光晕）；③ 鼠标跟随柔光（`mousemove` + `requestAnimationFrame` 节流写 `--mx/--my`，`radial-gradient` 跟随）；④ 统计数字滚动（`IntersectionObserver` 触发 + rAF 缓动递增）；⑤ 区块交错滑入（新增 `v-reveal-stagger` 指令，按序号设 `transitionDelay`）。
- **验证难点**：动态效果「截图看不出来」，容易被当成没实现。AI 提出用 CDP **读取运行时状态**取证：`getAnimations()` 里是否真有 `firefly` 动画、CSS 变量 `--mx/--my` 是否随鼠标变化、观察器触发后数字是否变成终值、列表项是否带上 `.reveal` 与递增延迟。
- **踩坑（我的诊断）**：调试期间截图反复超时、动画 `currentTime` 恒为 0——排查后确认**只有当前可见标签页才产生动画帧**，后台/被遮挡的标签页不会推进动画；此外该构建不支持页面级调试 WebSocket 与新建空白标签页。解法是经浏览器扩展打开并激活目标标签页，且**不在截图时全局暂停动画**。
- **结果**：5 项动态逐项取证通过，`prefers-reduced-motion` 下全部正确降级（萤火虫/柔光不渲染、进场动画关闭、数字直接显示终值）✅
- **评估**：这是一次「把不可见的动态效果变成可验证证据」的练习——也让我更理解「动画帧只在可见页面产生」这类浏览器渲染机制。

### 案例 H：课程要求反查 → 用「换分三件套」补齐差距

- **我的诉求**：课程要求里写着「basic testing」「feedback evidence」「Collecting feedback… making evidence-based improvements」，我想知道**自己到底缺哪一块**，不想凭感觉改。
- **AI 方案**：先**不写代码**，去查三家权威来源对齐「什么算好网站」——Core Web Vitals（`web.dev`）、WCAG 2.2（W3C）、十大可用性启发式（NN/g）——再逐条对照我的站点出一道「体检报告」，最后按「换分收益 ÷ 成本」排成三批，让我选先做哪一批。
- **我的决策**：选第一批「换分三件套」= A1 真实知识库内容 + A2 内容反馈闭环 + A3 最小自动化测试；第二、三批（页面标题、SEO 元信息、键盘焦点、404 页、CLS 治理等）先记下来不动。
- **AI 输出**：A1 把笔记改成 `src/content/notes/*.md` + `import.meta.glob` 内容管线（新增笔记不用改代码），写入 6 篇真实笔记，重写知识库页并加搜索/标签/空状态/`?note=` 深链；A2 新增三步式反馈组件挂在首页、项目页、每篇笔记末尾，并把 FormSubmit 出口抽成公共模块（顺手消掉和联系页的重复）；A3 接入 Vitest，写 5 个文件 31 条断言。
- **踩坑（我的诊断）**：① 截图调试时连续 4 次超时、截出来是旧图，我以为知识库白屏——查 DOM 发现内容一直都在（`#app` 内 8745 字符），真实原因是**后台标签页不产生动画帧**，把标签页切到前台即可；② 写站点数据测试时我以为 `site` 有 `role` 字段，一跑测试才发现实际叫 `tagline`——**测试帮我纠正了对自家代码的错误记忆**；③ 验证反馈组件时我要求**伪造 `fetch`**，避免演示时真往自己邮箱灌测试邮件。
- **结果**：31 条测试全绿，构建通过（CSS 27.63→32.77 kB，JS 163.01→181.95 kB，增量是 6 篇正文内联），浅色/深色下逐项截图取证 ✅
- **评估**：这次让我学到「**先对齐标准再动手**」比「想到哪改到哪」高效得多——AI 的价值不只是写代码，更在于帮我把模糊的「做好一点」翻译成可核对的清单。同时我也明确了边界：**反馈表模板我要求留空**，因为课程禁止编造真实用户验证，那一栏只能靠我自己找人试用后填。

### 案例 I：项目库扩充时，AI 帮我校正了两处「不严谨的自我描述」

- **我的诉求**：「把其他工作区里真实存在的项目都更新到主页，知识库内容也从这些工作区总结截取。」
- **AI 的第一步不是写代码，而是先盘点**：逐一核查 7 个工作区，区分「有真实产出」和「只是文件夹」。盘点结论是 —— 邮件处理工作区只有配置和空目录（`inbox`/`outbox`/`previews` 全空），**因此不写进主页**。这一步如果省掉，很容易凭印象凑出一个不存在的项目。
- **AI 随后的第二件事，是质疑我原来的表述**（这是我没想到但确实需要的）：
  - **股票量化的「112.74%」**：原来只写了数字。AI 指出这个数字**只在界面截图里留存、仓库里没有落盘的可复现结果文件**，而且它不是文档里主推的那个模型的成绩。修正为补全口径表（模型 = LightGBM 回归调参版、50 只、每 5 交易日调仓、2025-01-01~2026-08-14、基准 46.57%、超额 66.17%、回撤 -10.02%），并**主动补上同一个项目里那个「不好看」的数字**：可复现的传统规则策略 16.85%、同期基准 44.93%、**超额 -28.08%（跑输大盘）**。
  - **Carbon Brain 的模型效果**：原来写成「用机器学习预测并自动切换」，读起来像已完成。AI 核对后指出：饱和度模型按日期切分的测试集 **R² = -3.07（负值）**，依赖的突破时间预测模型**从未训练成功**，所以「自动切换」还在设计与阈值阶段。改成把「已做到的」和「没做到的」分开列，并**专门加一节「我做错的地方」**——我一开始把「物理换算链路跑通」当成了「模型可用」，这两件事必须分开验收。
- **我的判断**：全部采纳。我认为**这两个修正比多加两个项目更有价值**：主页是给人看的，但也是给我自己看的——把跑输大盘的数字和失败的模型如实写下来，比只挂一个漂亮数字经得起追问。
- **AI 还加了一道防线**：给测试加断言，强制检查二次开发类项目（TO-DO Panel、Claude Code 桌面版）的文案里**必须同时出现「上游/开源/第三方/MIT」和「不主张原创」两类表述**，防止以后改文案时不小心把边界抹掉。
- **踩坑（我的诊断）**：① `site.js` 里用反引号写了 `app.py`，破坏模板字符串导致构建直接失败——**构建报错比页面白屏友好得多**；② 批量转图片格式时只改了文件、忘了改代码里的引用路径，`.png` 指向已删除的文件（**改文件的动作和改引用的动作必须成对做**）；③ 想用 Node 直接 import `site.js` 检查文案，但 `import.meta.env` 在纯 Node 里不存在 → 改用**正则抽取模板字符串 + 单独跑 Markdown 解析**，绕开了对打包环境的依赖；④ 发现 Markdown 里 `**` 后面紧跟中文标点会导致加粗失效（CommonMark 规则），写笔记时需要注意。
- **结果**：主页项目从 2 个扩到 **6 个**（含一个可双击运行的完整模拟游戏），「关于」页从 2 段扩到 6 段，知识库 6 篇 → **10 篇**，测试 31 → **35 条断言全绿**，构建通过 ✅
- **评估**：这次最有价值的不是「加了内容」，而是**AI 指出了我对自己项目的描述不准确**。我原本以为盘点只是"把做过的东西列出来"，实际做下来发现真正的难点是：**哪些数字能说、怎么说才不算夸大**。

## 三、标准 3：对 AI 生成内容的理解（可解释）

我能用自己的话解释以下关键实现（可在 Demo Day Q&A 中被检验）：

| 内容 | 我的解释 |
|------|----------|
| **hash 路由** | 用 `#` 号切换视图，浏览器不向服务器请求新页面；因此部署在 `/homepage/` 子路径下不会 404，适合 GitHub Pages 这类静态托管。 |
| **深色模式** | 用 CSS 变量定义颜色，切换时给 `<html>` 加 `data-theme="dark"` 覆盖变量；选择存入 `localStorage`，刷新后保留。 |
| **`v-reveal` 滚动渐入** | 自定义指令，用 `IntersectionObserver` 监听元素是否进入视口，进入时加类触发 CSS 过渡。 |
| **`asset()` base 前缀** | 静态资源在子路径下要用 `import.meta.env.BASE_URL` 拼前缀，否则 `/avatar.jpg` 会指向站点根而不是 `/homepage/`。 |
| **联系表单提交** | 前端 `fetch` POST 到 FormSubmit 的 AJAX 端点，用 `_captcha:false` 关闭跳转式验证；成功判定 `data.success`，据此切 UI 状态。 |
| **V3 分层视差** | 用 `requestAnimationFrame` 监听滚动，把偏移量写入 CSS 变量（`--parallax` / `--portrait-parallax`），背景层与画框人像按不同速率 `translate3d`，形成纵深。 |
| **V3 双主题继承** | 新主题**保留旧变量名**并新增令牌，所以未改动的 V2 子页面能自动套用新配色；这是「用变量做设计系统」的直接收益。 |
| **原创素材与版权** | 背景图为 AI 原创生成、头像与项目图为我本人所有；没有把参考作品的图片素材用于成品，规避侵权。 |
| **V3 动态效果（纯 CSS/JS）** | 进场编排靠 `@keyframes` + `animation-delay`；萤火虫用 CSS 随机变量生成差异化光点；鼠标柔光用 `mousemove` + rAF 节流写 CSS 变量；数字滚动用 `IntersectionObserver` + rAF 缓动；交错滑入用自定义指令按序号设 `transitionDelay`。全程未加依赖，并用 `prefers-reduced-motion` 统一下线。 |
| **知识库内容管线** | 用 `import.meta.glob('../content/notes/*.md', { query:'?raw', eager:true })` 在**构建时**把全部 Markdown 读成字符串，再自己解析文件头的 frontmatter（`key: value` / `[a,b]`）。所以「加笔记」只是加文件，不需要改代码，也不需要运行时请求。 |
| **笔记深链 `?note=`** | 选中哪篇写进地址栏的 query（`#/knowledge?note=xxx`），刷新或把地址发给别人能直接打开同一篇；从 query 读不到时回退到第一篇。 |
| **内容反馈闭环** | 三步式组件（先表态 → 选填原因 → 感谢），反馈入口贴在内容末尾而不是单独页面，降低反馈门槛；提交内容带 `page`/`item`/`url`，收到邮件时能定位来源；本机用 `localStorage` 记住已反馈，避免重复打扰。 |
| **表单出口抽公共模块** | `src/data/feedback.js` 统一 `FORM_ENDPOINT` 与成功判定，联系表单和反馈组件共用一份配置，换后端只改一处。 |
| **自动化测试为什么这么写** | 只测「容易改坏、又不靠肉眼」的地方：内容解析、数据完整性、路由表、表单成功/失败判定、组件状态流转。测试只为开发服务，进 `devDependencies`，不进构建产物。 |
| **为官一方怎么塞进静态页面** | 游戏本体是**单文件 HTML**（原生 JS 的 SVG 渲染 + 配置驱动的数值系统），所以能直接放进 `public/projects/` 当静态资源用，不需要后端也不需要服务器逻辑。这也是我做这个项目时的一个关键设计决策——**不依赖游戏引擎**，才能这样直接嵌进主页。 |
| **为什么要把「上游是谁」写进正文** | 二次开发和"偷来当自己的"是两件事。技术上我改的是本地文件、加的是自己的补丁；但**表述上必须让人一眼看出上游是谁**，否则就是在借别人的成果抬高自己。所以标题、正文第一段、`role` 字段三处都写明了来源。 |
| **加了断言的测试有什么用** | 普通测试只证明"现在对"；**加了约束的断言能防止以后改错**。比如"二次开发项目必须注明上游"这条，它拦的不是 bug，而是**文案被无意改回成夸大表述**——这种问题肉眼评审很难发现。 |
| **项目图片来源与口径** | 6 个项目的展示图全部来自我本地真实的运行截图或界面截图，不是示意图；涉及数字的文案统一补口径（模型、区间、基准、条件），不只写结果。 |

## 六、反思与限制（诚实复盘）

- **做得好的**：AI 输出的每个方案我都做了验证，尤其部署与联网服务环节，形成了「提出→实测→修正」的闭环；V3 重设计时主动接受「学习模式 ≠ 复刻表达」的合规边界；项目扩充时接受 AI 对我原有表述的两处校正，把跑输大盘的数字和失败的模型如实写进主页。
- **AI 的局限**：AI 默认方案往往通用但**不了解本环境的网络与仓库配置**（如 Actions 与部署源冲突、Formspree 验证缺陷、代理端口），必须由人核验；AI 首次判断截图错位时也误以为是页面 CSS 问题；AI 一开始并不了解其他工作区里到底有没有真实产出，**必须靠实际盘点而不是靠推测**。
- **我的不足**：早期未及时核验「部署源」概念，走了 Actions 弯路；调试时一度把工具异常当成产品缺陷；知识库长期挂着占位内容没有及时替换成真实笔记；**主页上的项目长期只有 2 个、没体现真实工作量**；表述不够严谨（只写亮眼的数字，没写口径和失败的部分）。
- **下一步**：继续把「先验证关键假设、区分工具问题与产品问题」固化为习惯；补齐权威标准体检中已定位但未做的项（每页标题、SEO 与分享元信息、键盘焦点与跳转链接、404 页、图片 CLS 治理、README 重写）；**真实收集不少于 5 条用户反馈**填入《用户反馈与改进记录》，完成「收集 → 评估 → 有依据地改进」的闭环；数字人对话先做路线决策（关键约束：**API Key 不能放在前端**，需加 Serverless 中间层）。
