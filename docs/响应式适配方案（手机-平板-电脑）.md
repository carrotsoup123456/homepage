# 响应式适配方案：手机 / 平板 / 电脑

> 这份文档回答一个问题：**同一个页面在手机、iPad、电脑上打开，排版差在哪、哪些是真问题、怎么改、改完怎么证明改好了。**
> 全部结论都来自实测（脚本模拟 9 种屏幕 × 5 个页面），不是靠猜。测量方法写在第二节，可以自己复现。
> 本方案只提改动建议，**尚未修改任何代码**。

---

## 一、一句话结论

| 设备 | 现状 | 结论 |
| --- | --- | --- |
| 电脑（1440 / 1920 / 2560） | 版心 1140px 居中，无横向滚动，主视觉两列正常 | **没问题**（只有超大屏两侧留白偏多，属审美） |
| iPad 横屏（1024） | 两列布局，桌面导航，正常 | **没问题** |
| iPad 竖屏（768） | 单列 + **汉堡菜单** | 能用，但和 iPad Air（820）用了两套导航 |
| iPad Air 竖屏（820） | 单列 + **桌面导航** | 和 768 的 iPad 不一致 |
| 手机（375 / 390 / 414 / 430） | 首页、知识库、联系、详情页正常；**「关于」页装不下** | **1 个真 bug** + 一批尺寸问题 |

**真 bug 只有 1 个**：「关于」页的工作列表在窄屏上装不下——实测这段内容有一个 **459px 的最小宽度**，而手机屏幕只有 320–430px。表现有三种：页面能横向拖动、浏览器自动缩放把字变小、或者标题被挤成**一个字一行的竖排**。

其余都不是"坏了"，而是"能用但不够好"：点击区域偏小（手机上 13–22 个小于 44px）、知识库小字偏小（45 处 11.5px）、首屏在 iPhone SE 上比屏幕高 201px、iPad 竖屏与 iPad Air 用了两套导航。

## 二、怎么测的（可复现）

用 DeepWorks 内置浏览器的调试接口，把页面模拟成 9 种屏幕，逐页量 4 件事：

1. **横向溢出**：`document.documentElement.scrollWidth` 是否大于视口宽度（超出多少 px）
2. **点击区域**：所有 `a / button / input` 的宽高，统计小于 44px 的个数
3. **字号**：所有文字节点的计算字号，统计小于 12px 的个数
4. **布局列宽**：主视觉两列、统计卡、特色行、知识库侧栏的实际宽度

覆盖范围：

| 类别 | 模拟尺寸 |
| --- | --- |
| 手机 | 375×667（iPhone SE）、390×844（iPhone 14）、430×932（iPhone 15 Pro Max） |
| 平板 | 768×1024（iPad 竖）、820×1180（iPad Air 竖）、1024×768（iPad 横） |
| 电脑 | 1440×900、1920×1080、2560×1440 |

脚本 `.deepworks/cdp-tool/resp_audit.mjs`（9 设备 × 5 页面）+ `.deepworks/cdp-tool/resp_probe320.mjs`（最窄三档 320/360/414），结果明细在 `.deepworks/tmp/resp-audit.log`。

**测量时要注意的坑**（影响你怎么看数字）：手机模拟下，如果页面装不下，浏览器不会老实地显示滚动条，而是**整体缩小到能装下**，这时 `window.innerWidth` 会读到 459（我设的是 390）。所以"溢出多少 px"这个数字会随量法变化，但**"这段内容最小宽度 459px"这个结论在 320 / 360 / 375 / 390 / 414 五种宽度下完全一致**——这才是要修的东西。

另外：模拟器终究是模拟器，**改完必须在真机上再看一遍**，尤其是 iPhone 地址栏伸缩这件事（见 P1-2）。

## 三、真问题清单（按严重度排序）

### P0-1 「关于」页在手机上装不下 ⚠️ 唯一的真 bug

**实测证据**

| 屏幕宽 | 页面内容宽 | 结果 |
| --- | --- | --- |
| 375 | 459 | 横向溢出 **84px**；标题 224px 正常，但角色标签右边缘顶到 341 |
| 390 | 459 | 横向溢出 **69px**；**《为官一方》标题被压成 32×331 的竖排窄条** |
| 414 | 459 | 浏览器缩小塞下；标题仍是 32×331，文字块只剩 24px |
| 768 及以上（iPad / 电脑） | 753 | 正常，文字块 395–651px |

**为什么**（根因，只有三行 CSS）

工作列表每条是「图标 | 文字块 | 角色标签」横着排：

```css
.work-item { display: flex; gap: 16px; }      /* 三个东西排一行 */
.work-body { flex: 1; min-width: 0; }         /* 文字块：初始宽度 0，可以被压到 0 */
.work-role { flex-shrink: 0; }                /* 角色标签：不许被压缩 */
```

- 文字块的"初始宽度"是 0，所以它可以被压成 0px（标题就一个一个字竖着排）；
- 角色标签"不许压缩"，所以它的宽度就锁死在**文字撑满的最大宽度**——最长的那条（TO-DO Panel）实测 **366px**；
- 366 + 44（左边距）+ 40（卡片内边距）≈ 459px > 手机宽度 → 装不下。

`@media (max-width: 640px)` 里其实已经写了 `flex-wrap: wrap`，**但它救不了**：文字块的初始宽度是 0，"永远装得下"，浏览器找不到换行的理由。

**改法（✅ 已按此实施，2026-09-25）**

实际用的是网格，不是一开始设想的 `flex-direction: column`——因为列布局会把图标孤零零地留在第一行。网格让「图标 + 标题/说明」仍然同一行，角色标签独占第二行：

```css
@media (max-width: 640px) {
  .work-item {
    display: grid;
    grid-template-columns: auto 1fr;   /* 第一行：图标 | 标题与说明 */
    gap: 8px 12px;
    align-items: center;
  }
  .work-icon { grid-area: 1 / 1; }
  .work-body { grid-area: 1 / 2; }
  .work-role {
    grid-area: 2 / 1 / 3 / 3;          /* 第二行：标签独占整行 */
    justify-self: start;               /* 胶囊按内容收缩，不拉满 */
    margin-left: 0;                    /* 去掉原来那个 44px 魔法数字 */
  }
}
```

标签独占整行后，它想换行就换行，366px 那条也装得下；文字块在 `1fr` 列里拿到全部剩余宽度，标题不再被压成竖排。

**实施结果**（CDP 实测，`resp_verify_final.mjs` / `verify_last2.mjs`）：375 溢出 **84 → 0**、390 溢出 **69 → 0**、320 / 360 / 414 同样为 0；标题从 32×331 竖排恢复为 224×31 正常横排；`work-body` 从 0~24px 恢复到 188–282px。

**再加一道保险**（治别的页面同类的毛病）

```css
html { overflow-x: clip; }
```

>`clip` 是 `hidden` 的"只切不滚动"版本。用 `hidden` 有可能影响吸顶导航（`position: sticky`），`clip` 不会。

**工作量**：约 15 分钟（改 1 个文件的 1 段媒体查询）。

**验收**：375 / 390 / 414 宽下，文档宽度 = 视口宽度（溢出 0）；5 条工作项的标题宽度都 > 100px（不是竖排）。**✅ 已全部达标（2026-09-25 实测，数值见上）。**

**顺手对照一下标准**：这一条同时违反 WCAG 2.2 的 **1.4.10 回流（AA）**——页面在 320px 宽下必须不需要横向滚动就能用（表格、图片这种二维内容除外）。所以它不只是"手机上不好看"，而是实打实的不达标。

### P0-2 可点区域太小 ⚠️

**实测证据**（这些元素在每个页面都有，因为都在顶部导航里）

| 元素 | 实测尺寸 | 判定（WCAG 2.2 AA：≥24×24） |
| --- | --- | --- |
| 汉堡菜单 `☰` | **23×31** | ✗ 宽 23 < 24 |
| 导航链接（首页/关于/知识库/联系） | **30×21** | ✗ 高 21 < 24 |
| 主题切换 `☀️` | 36×36 | 达 AA，但不达推荐的 44 |
| 姓名（回首页的链接） | 65×36 | 接近 |
| 「← 返回首页」（详情页） | 85×28 | ✗ |
| 知识库筛选按钮 | 52×32 / 64×32 / 37×32 | ✗ |
| 首页项目标题链接 | 339×33（手机）/ 452×44（电脑） | 手机高 33：达 24，不达 44 |
| 关于页工作项标题 | 224×23（手机 / iPad 同样是 23） | ✗ 高 23 < 24 |
| 反馈按钮 👍 / 🤔 | 85×43 / 113×43 | 接近 |

（已经达标的：首页的「查看详情 →」按钮、知识库条目整块、主视觉的两个大按钮，都在 44px 以上。）

小屏下"小于 44px 的可点元素"总数：手机首页 **13** 个、知识库 **22** 个、关于页 11 个、详情页 10 个、联系页 7 个。

> 标准怎么读：WCAG 2.2 的 2.5.8「目标尺寸（最低）」是 **AA**，要求 24×24 CSS px；2.5.5 是 **AAA**，要求 44×44。苹果和谷歌的设计规范都建议**至少 44**，因为手指的触点在 40–48px 之间才不容易点错。

**改法（✅ 已实施，2026-09-25）**：手机上把目标撑大，桌面鼠标环境一个像素都不动。所以统一放在 `@media (max-width: 768px)` 里（不能用 640——导航断点调到 640 是 P2-1 的事，641–768 之间现在仍是汉堡菜单）。

```css
@media (max-width: 768px) {
  /* 汉堡键 23×31 → 44×44。justify-content: flex-end 让 ☰ 停在原位，多出来的宽度往左扩 */
  .nav-toggle { display: flex; align-items: center; justify-content: flex-end;
                min-width: 44px; min-height: 44px; }
  .theme-toggle { width: 44px; height: 44px; }            /* 36×36 → 44×44 */

  /* 展开后的菜单每条 44px 高；下划线的锚点要跟着文字走（bottom 相对盒子，盒子高了 23px） */
  .nav-links a { display: inline-flex; align-items: center; min-height: 44px; }
  .nav-links a::after { bottom: calc(50% - 16px); }

  .back-link { padding: 12px 0; }                          /* 85×28 → 85×52 */
  .filter-chip, .fb-btn { min-height: 44px; }              /* 32/43 → 44 */

  /* 纯文字链接是行内元素：加纵向内边距不影响排版，可点区域 23 → 31px */
  .work-title { padding: 4px 0; }
}
```

**实施结果**（CDP 实测）："触控 < 44px"手机首页 **13 → 6**、知识库 **22 → 2**、关于页 11 → 6；剩下的全部是 ≥24×24 的达标项（姓名链接 65×36、项目标题链接高 33、"AI"筛选片 37×44、工作项标题高 31）——即 WCAG 2.2 AA（2.5.8）全过，且关键控件（汉堡/主题/菜单行/筛选/返回/反馈按钮）都到了 44。

**验收**：脚本里"触控 < 44px 数量"，手机首页从 13 降到 ≤4（剩下的只有正文里的行内链接）。**实际剩 6 个，全部 ≥24×24（见上）——比"≤4"宽一点，但每一个都过 AA；正文行内链接按标准本就只需 24×24，硬撑到 44 会破坏排版。**

### P1-1 知识库的小字太多

**实测证据**：知识库页有 **45 处**文字小于 12px（最小 **11.5px**），来源是两个：`.kb-item-tag`（`#AI`、`#量化` 这类标签）和 `.kb-item-min`（阅读时长），都是 `0.72rem = 11.5px`。首页 4 处、关于页 5 处，来自 `.eyebrow`（`MY APPROACH` 这类小标题），同样是 11.5px。

**改法**：

```css
@media (max-width: 640px) {
  .kb-item-tag, .kb-item-min { font-size: 0.8rem; }          /* 11.5 → 12.8px */
  .eyebrow { font-size: 0.76rem; letter-spacing: 0.2em; }    /* 11.5 → 12.2px */
}
```

理由：正文 14–15px 没问题，但"标签、阅读时长"这类辅助信息在手机上小于 12px 就很难看清；再加上手机常常是平放着看的，距离比坐着看电脑更远。

**工作量**：10 分钟。**验收**：手机上小于 12px 的文字从 45 降到 0。

### P1-2 首屏在矮屏手机上比屏幕高

`.hero-v3 { min-height: calc(100vh - 74px); }`

`100vh` 在手机上取的是**最大视口高度**（把会收起来的地址栏也算进去），所以首屏总会比真正看得见的那块高 60–100px；再加上内容本身的高度：

| 设备 | 视口高 | 首屏实际高 | 说明 |
| --- | --- | --- | --- |
| iPhone SE 375×667 | 667 | **868** | 比屏幕高 201px，「查看详情」按钮在屏幕外 |
| iPhone 14 390×844 | 844 | 854 | 高 10px（最小高度算出来 770，被内容顶到 854） |
| iPad 竖 768×1024 | 1024 | 950 | 正好一屏 |
| iPad Air 竖 820 | 1180 | 1106 | 正好一屏 |
| 笔记本 1440×900 | 900 | 826 | 正好一屏 |
| 宽屏 2560×1440 | 1440 | 1366 | 一屏全是主视觉（内容上限 1140px，两侧各留约 700px） |

**改法**：

```css
.hero-v3 { min-height: calc(100svh - 74px); }   /* svh：地址栏显示时的高度，最稳 */

@media (max-height: 720px) {                     /* 矮屏手机别硬撑一屏 */
  .hero-v3 { min-height: auto; padding: 44px 0 56px; }
}
```

>`svh / lvh / dvh` 是新的视口单位：`svh` = 地址栏**显示**时的高度（最小），`lvh` = 地址栏**收起**时的高度（最大），`dvh` = 跟着地址栏实时变。首屏用 `svh` 最保险（不会闪现），要"始终铺满"就用 `dvh`。

同一个毛病还有一处：`KnowledgeView.vue:239` 的 `max-height: calc(100vh - 120px)`（知识库左侧的笔记列表），也要一起改成 `100svh`。

**工作量**：10 分钟。**验收**：iPhone SE 模拟下首屏高度 ≤ 视口高度；真机上打开首页，「查看详情」按钮在第一屏内。

### P1-3 移动菜单的三个小毛病

1. **菜单位置写死 74px**：`.nav-links { inset: 74px 0 auto 0 }`，而头部实际是 **75px**（`.nav { height: 74px }` + 1px 下边框）。现在只差 1px 看不出来，但以后改字体、加内边距就会明显错位。
   **改法**：把这个数字收成一个变量，两处共用。
   ```css
   :root { --header-h: 74px; }
   .nav { height: var(--header-h); }
   .nav-links { inset: var(--header-h) 0 auto 0; }
   ```
2. **打开菜单不锁背景**：菜单盖在页面上，手指一滑背景跟着滚，容易滑着滑着就找不到菜单了。
   **改法**：`SiteHeader.vue` 里监听 `menuOpen`，打开时给 `<body>` 加一个 `menu-open` 类：
   ```css
   body.menu-open { overflow: hidden; }
   ```
3. **收起状态的菜单还能被 Tab 选中**：收起时靠 `transform: translateY(-160%)` 挪出屏幕，元素还在页面里，所以键盘用户按 Tab 会**跳进一个看不见的菜单**（焦点消失了）。
   **改法**：收起时补 `visibility: hidden`（并加进 transition，开关动画不受影响）。这里**没用 `inert`**：`inert` 绑的是 `menuOpen` 这个状态，而"菜单该不该藏"取决于屏幕宽度——如果手机横过来（宽度超过断点）时 `menuOpen` 恰好是 true，桌面导航会被 `inert` 锁死。`visibility` 写在窄屏媒体查询里，宽度一变规则自动失效，不会留后遗症。这是修 WCAG 2.4.3「焦点顺序」的问题。

**✅ 三项已全部实施（2026-09-25）**，实测（无过渡注入下读规则匹配）：收起 `visibility: hidden` 且链接不可聚焦 ✓；打开 `visibility: visible`、菜单顶边正好 74px（变量生效）✓、`body.menu-open` + `overflow: hidden` 锁住背景 ✓；Esc 关闭、body 类移除、焦点还回汉堡键 ✓。

**工作量**：三处共约 20 分钟。**验收**：打开菜单后背景不滚；收起菜单后按 Tab，焦点不会跑到屏幕外面。

### P2-1 iPad 竖屏与 iPad Air 用了两套导航

导航的断点是 `@media (max-width: 768px)`：

| 设备 | 视口宽 | 导航形态 | 主视觉 |
| --- | --- | --- | --- |
| iPad 竖屏 768 | 768 | **汉堡菜单** | 1 列 |
| iPad Air 竖屏 820 | 820 | **桌面导航** | 1 列（`≤900` 折叠） |
| iPad 横屏 1024 | 1009 | 桌面导航 | 2 列 |

同一类设备（iPad）因为差 52px 就换了一套完全不同的导航。而且 iPad 竖屏根本不需要汉堡键——768px 宽装 4 个导航词加一个主题开关绰绰有余（实测这 4 个词总宽不到 200px）。

**改法**：把导航的断点从 768 收到 640，和"手机"的定义对齐。

```css
@media (max-width: 640px) {   /* 原来是 768 */
  /* ...汉堡菜单那一整段... */
}
```

`@media (max-width: 900px)` 的单列折叠**不要动**——那个管的是"内容太宽"，和导航是两件事。

**工作量**：5 分钟。**验收**：768 / 820 宽下都是桌面导航，只有 ≤640 才是汉堡键。

### P2-2 iPhone 的刘海与底部横条没适配

`index.html` 的 viewport 没有 `viewport-fit=cover`，全站也没有用任何 `env(safe-area-inset-*)`。底部固定的「回到顶部」按钮是 `.back-to-top { position: fixed; bottom: 28px }`，在 iPhone 上会和底部那条 Home 横条挤在一起。

**改法**（两处）：

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
```

```css
.back-to-top { bottom: calc(28px + env(safe-area-inset-bottom)); }
.container {
  padding-left: max(28px, env(safe-area-inset-left));
  padding-right: max(28px, env(safe-area-inset-right));
}
```

**工作量**：5 分钟。**验收**：真机（或模拟器选中带刘海的机型）上，底部按钮与横条不重叠。

### P2-3 超大屏两侧留白偏多

版心 `--max-width: 1140px`。2560 宽屏下两侧各约 700px 空白，主视觉文字列固定 564px。

## 四、看着像问题、其实不是（别乱改）

脚本会把这些报成"可横向滚动"，但它们都是**有意设计**，外面套了 `overflow-x: hidden` 裁掉，不会产生横向滚动条：

| 元素 | 溢出的量 | 为什么不是问题 |
| --- | --- | --- |
| `.marquee`（技能跑马灯） | 2054px vs 视口 375–1905 | 就是要无限滚动 |
| `.hero-v3` / `.fireflies`（主视觉光斑、萤火） | 比视口宽 16px | 光效故意超出边缘，切掉才自然 |
| `.hero-bg`（首屏背景图） | 2560 宽屏下 2647px | 背景铺满 |

另外这些是**做对了**、别改：

- 详情页表格、知识库长代码块已经有 `overflow-x: auto`，手指可以横滑 —— 这正是 WCAG 1.4.10 允许的例外（二维内容）
- 桌面段落宽度限制在 52–56 个字符（`max-width: 52ch/56ch`）——**好**做法，别改成 100%

## 七、不建议做的

- **不要按设备写 CSS**（给 iPhone 一套、iPad 一套）。手机型号和屏幕宽度的对应关系一直在变，按"宽度区间"写才稳。
- **不要用 JS 判断 UA**（`navigator.userAgent`）来切布局。新设备、折叠屏、iPad 上的"桌面模式"都会判错。
- **不要为了这几条引入 UI 框架**（Tailwind / Bootstrap）。现在的问题就是 4 类 CSS 规则的事，引框架等于把整个工程重写一遍，还会把"为什么这么写"藏起来——对课程里"能讲清楚自己做了什么"这件事是负分。
- **不要用 `overflow-x: hidden` 盖住 P0-1**。那样只是不滚了，标题照样是竖排；要修的是"为什么装不下"。

## 九、设计说明：现在是什么设计、打算怎么改、代价是什么

这一节回答"你的设计是什么 / 怎么实现 / 有什么后果"。前面几节讲的是"哪里坏了"，这一节讲"为什么这么修"。

### 9.1 现在的设计（现状）

方向是对的，问题在三个细节：

**做法**：一套 HTML + 一套 CSS，靠"宽度阈值"决定要不要折叠——同一个页面，屏幕窄到某个数就把两列变一列、把导航收成汉堡菜单。CSS 里一共出现了 6 个阈值：`560 / 640 / 720 / 768（两处）/ 860 / 900（三处）`。

**问题一：阈值数字散落，没有体系**。导航的阈值是 768，内容的阈值是 900 —— 两个数字谁管什么、为什么是这两个数，代码里看不出来。结果就是 iPad 竖屏 768 落进"手机"这一档用了汉堡菜单，而 iPad Air 820 落进"桌面"这一档用了完整导航：**同一种设备，两种形态**，原因是它们刚好卡在 768 这条线的两侧。

**问题二：尺寸写死、没有"能收缩"的约束**。头部高 74px、菜单位置也写死 74px（实际 75px）、主题按钮 36×36、汉堡键完全靠 `☰` 这个字撑出 23×31。写死本身没错，错在**同一件事在两个地方各写一遍**，且布局里没有"装不下时怎么办"的兜底——所以「关于」页遇到一条 366px 的长标签就崩了。

**问题三：用绝对单位描述会变的设备**。`100vh` 在手机上包含会收起的地址栏；`74px` 的头高在换字号后就会变；刘海和底部横条完全没有被考虑。

一句话：**它不是"没做响应式"，是"做了响应式但没有规则"。**

### 9.2 打算怎么实现（三层，都不改视觉风格）

| 层 | 做什么 | 具体手段 |
| --- | --- | --- |
| 一、阈值成体系 | 把 6 个散落的数字收成 3 档含义 | 手机 ≤640 / 平板 641–900 / 桌面 ≥901。**导航**只管"能不能装下 4 个词"，**内容**只管"两列会不会挤"，两件事分开定 |
| 二、让布局天生能伸缩 | 不再依赖写死尺寸和魔法数字 | 给换行一个真实理由（`flex: 1 1 100%`）、该缩的允许缩（`min-width: 0`）、该有下限的给下限（`min-height: 44px`）、同一件事只写一处（`--header-h` 变量） |
| 三、单位跟着设备走 | 用"描述设备"的单位代替"描述像素"的单位 | `svh` 代替 `100vh`（首屏）、`env(safe-area-inset-*)` 处理刘海与底部横条、`max()` 组合最小值 |

**明确不做的四件事**：不改配色与字体、不动任何文案与内容、不引入任何依赖或框架、不按设备型号或 UA 判断（只按窗口宽度）。

### 9.3 后果：会变的、不会变的、代价

**会变的（用户看得见）**

| 变化 | 说明 |
| --- | --- |
| 手机「关于」页改成**一列** | 每条工作项从"图标｜文字｜标签"横排变成上下堆叠；卡片变高、整页变长（这是你选的方案） |
| 手机上点击区域变大 | 汉堡键从 23×31 撑到 44×44、主题键 36→44、导航每行 21→44 高。视觉上图标本身不变大，只是**周围可点的空白变大**，顶部右侧元素的间距会略松 |
| 知识库手机上略大略高 | 筛选按钮 32→44 高，标签字号 11.5→12.8px；筛选那一行占的高度会增加 |
| 首屏高度（B 档） | iPhone 上首屏从"比屏幕高"变成"刚好一屏"，主视觉内容会往上提一点 |
| iPad 竖屏导航（C 档） | 从汉堡菜单变成完整导航，导航词直接显示在顶部 |

**不会变的**

电脑端观感、配色、字体、文案、所有内容、iPad 横屏的两列布局、部署方式（还是纯静态文件，推送后线上立即生效）。

**代价与风险（老实说）**

1. **可以整体回退**：改动全在样式与头部一处交互，用 git 一条命令就能退回现在的样子，不存在"改坏了回不来"。
2. **必须复验**：跑同一套脚本对比 4 个指标，跑 `npm test` 确认 61 条断言不挂，再用手机实际打开一遍。这一步不能省。
3. **时间比"改"本身长**：写 CSS 约 50 分钟（A 档），但复验 + 真机自测 + 把 before/after 数字写进课程材料，合计约 1.5–2 小时。课程要的是"能证明的改进"，只改不记录等于白干。
4. **`html { overflow-x: clip }` 的副作用**：它会切掉任何跑到视口外的装饰元素。现在跑出去的光斑、跑马灯本来就是被切的，所以肉眼无变化；但以后若想做一个"故意探出边缘"的效果，会被它切掉。旧版 Safari（<16）不支持 `clip`，会退化成"不裁切"——不会更糟。
5. **断点收到的代价**：把导航阈值从 768 收到 640 之后，641–768px 这一段（含 iPad 竖屏）用的是完整导航。实测 4 个导航词总宽不到 200px、logo 约 65px，641px 装得下；但如果以后导航加到 6–7 项，这个宽度就要重新算。
6. **一处偏差无法完全消除**：手机上"触控 < 44px"数量没有降到 0（首页 6、知识库 2、关于 6），剩下的全部是 ≥24×24 的达标项：正文里的行内链接本质是文字的一部分，把它撑到 44px 会破坏排版；这类元素按标准只需满足 24×24。关键控件（汉堡/主题/菜单行/筛选/返回/反馈按钮）已全部到 44。

### 9.4 为什么不用别的做法

- **按设备写 CSS**：要维护"iPhone 一套、iPad 一套、安卓一套"，设备一更新就失效。
- **JS 判断 UA**：折叠屏、iPad 的"桌面模式"、安卓平板都会判错。
- **引 Tailwind / Bootstrap**：现在的问题只是 4 类 CSS 规则，引框架等于把整个工程重写，还会把"为什么这么写"藏进框架里——课程里要讲清楚自己做了什么，这是负分。
- **用 `overflow-x: hidden` 直接盖住**：那样只是不滚了，标题照样是竖排，等于没修。
